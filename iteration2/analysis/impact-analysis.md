# Iteration II requirements impact

Authority: supplied `p02.iter2.pdf`, pp. 2–5 (no `p02.iter2(1).pdf` was present). Starting points: `iteration1/UC1-request-appointment.docx`, `UC2-conduct-consultation.docx`, `UC3-issue-referral.docx`, `non_critical_usecases.md`, `SOEN342-SSDs-and-Operation-Contracts.pdf`, and the embedded editable models in `UML use case.drawio.png` and `DMupdated.drawio.png`. The latter already adds TimeSlot, WaitlistEntry and Resource to the original `DomainModel.drawio.png`.

| Change | Effect on the original artifacts |
| --- | --- |
| Explicit availability | Refine the original Schedule working windows into dated TimeSlots with start/end, location and OPEN/BOOKED occupancy, as already begun in DMupdated and implemented by Part B. Making and searching availability use reserved SO25/SO26. Keep professional specialties and practice locations. |
| Booking | UC1 still checks service/referral eligibility and patient conflicts. CO1 offers open TimeSlots; CO2 selects one unambiguously, rechecks it, associates the Appointment and changes occupancy to BOOKED. Requested appointments already hold time in Iteration I. SO16 rescheduling must atomically release the old slot and occupy the new one, preserving history. |
| Cancellation | Revised CO17 retains the Appointment and Referral links, marks cancellation, releases its slot and resource allocations, and returns eligible waitlisted patients in priority order. It creates no replacement Appointment. Telephone acceptance and ordinary booking remain separate events. |
| Waiting lists | Extend UC1's no-availability branch with patient-requested placement. Add WaitingList, criteria/service-bearing WaitlistEntry and telephone WaitlistOffer. SO27–SO30 cover placement, eligibility, offer outcomes and staff priority changes. Declining does not itself remove a patient: removal is a staff choice. |
| Resources | Refine DMupdated's direct service–resource requirement into ResourceRequirement, with kind and quantity, satisfied by predefined room/equipment/role units. Staff can inspect and select resources (SO33/SO34); booking checks availability and forms allocations. A human resource denotes a role unit, never a named employee. Detailed design and implementation are deferred. |
| CSV | SO31 imports availability, then booked appointments, then waitlist patient information; SO32 exports every slot, including occupied ones. RAMQ is optional; Patient–Insurance changes from 0..1 to 0..*. Sample waitlist rows lack service, target criteria and priority, so they cannot establish eligible entries or valid clinical Referrals. |

The updated use-case diagram preserves all three critical and nine non-critical Iteration I use cases and their existing include/extend relationships. The domain model preserves the original care, referral, billing and audit concepts. CSV is an input/output mechanism, not a new conceptual service or domain entity. See [use-case-scenarios.md](use-case-scenarios.md), [operation-contracts.md](operation-contracts.md) and the adjacent SVG models.

Part A adds CSV integration and realizes only UC3 SO08–SO10 at design level. Part B's Java files and `ats.App` are retained. Part C owns the integrated menu, booking/consultation realizations, shared application state and consolidated design class diagram. This Part A contribution does not complete the assignment's entire team submission.

Policies the assignment leaves open are labelled conventions in the scenarios/contracts: priority scale and tie ordering, precise waitlist eligibility, duplicate criteria, and resource selection. Original referral expiry/open-status rules remain unresolved. The PoC uses Part B's BOOKED Appointment status to represent occupied appointments; it does not silently add Iteration I's Requested/Confirmed lifecycle, clinical records or audits to the existing skeleton.
